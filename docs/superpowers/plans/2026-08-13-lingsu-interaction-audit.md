# 灵溯交互问题分析、执行状态与下一步计划

更新时间：2026-08-13

## 1. 文档目的

这份文档把当前灵溯项目的真实状态、已发现的交互问题、已经落地的修复以及下一阶段的验收任务集中记录下来。它对应的核心问题是：

1. 操作后没有明确反馈，用户不知道操作是否成功、失败后应该怎么处理。
2. 任务完成度和任务状态缺少差异化表达，用户不能快速判断“现在该做什么”。
3. 学生首页、项目概览、任务地图和材料档案重复表达同一信息，页面之间来回切换但决策没有推进。

本轮的目标不是增加更多页面，而是让三端围绕各自唯一的工作问题形成闭环：

```text
学生：看见下一步 → 开始任务 → 提交证据 → 查看反馈 → 修订/解锁
教师：看到需要判断的事项 → 查看证据 → 通过/打回 → 让学生继续
平台：看到需要治理的对象 → 确认影响 → 执行变更 → 查看结果
```

## 2. 当前项目基线

### 2.1 技术边界

- 前端：Vue 3、Vite、TypeScript、Element Plus、Pinia、Vue Router。
- 后端：Django REST Framework、PostgreSQL、Celery、Redis。
- 文件与异步任务：保留私有附件、分片上传、病毒扫描、解析和报告导出的后端边界。
- 本轮交互专项：优先处理前端信息架构、状态呈现和反馈闭环，不把 Django 接口替换为新的假数据层。

### 2.2 三端路由边界

| 端 | 入口 | 主要职责 | 不应出现的内容 |
| --- | --- | --- | --- |
| 学生端 | `/student/*` | 建项目、完成任务、提交材料、查看修订和报告 | 教师审核收件箱、学校授权配置 |
| 教师端 | `/teacher/*` | 认领项目、确认成员、审核材料、指导风险 | 学生任务编辑器、平台授权配置 |
| 平台端 | `/platform/*` | 创建学校、授权启停、赛事公告、案例治理 | 学生任务地图、材料编辑、教师审核队列 |

入口 `/` 根据登录身份进入对应门户；没有会话进入 `/login`。门户内部不再通过“演示角色切换器”伪造权限。

### 2.3 当前已验证的后端基础

- 学校范围过滤、角色权限、项目草稿/待认领/进行中、教师认领、材料提交与审核、公开案例和 AI 记录已有 Django API。
- 后端核心测试当前为 81 个通过，`manage.py check` 和迁移检查通过。
- 授权学校的写入限制、历史内容只读语义已有后端实现基础；后续需继续补齐统一错误码和审计事件。服务健康接口已完成首版。

### 2.4 当前已验证的前端基础

- 前端已有学生、教师、平台三套布局和角色守卫。
- 已增加 `FeedbackBanner`、`TaskStatusCard`、反馈状态模型和交互文案模型。
- 学生首页已改成“今日行动台”；任务页已区分开始、待审核、需修订、已通过和未解锁。
- 教师项目详情已从教师工作台独立出来，显示团队、阶段、材料和风险摘要。
- 顶栏品牌、通知和帮助入口已有真实行为；平台停用、邀请码重置、赛事发布/撤回使用确认弹窗。
- 搜索按钮已执行检索，并显示成功、无结果和失败反馈。

## 3. 问题分析：为什么原页面不好用

### 3.1 第一性原理判断

用户不是来“浏览系统模块”的，而是来完成一个结果。每个页面必须只回答一个主要问题：

| 页面 | 唯一问题 | 页面内的唯一主行动 |
| --- | --- | --- |
| 学生首页 | 我今天最应该做什么？ | 开始/继续/修订一个优先任务 |
| 项目概览 | 项目走到哪里、谁参与、卡在哪里？ | 进入研究旅程 |
| 任务地图 | 研究路径中下一项是什么？ | 进入一项任务 |
| 任务页 | 如何完成并提交这项证据？ | 保存或提交材料 |
| 材料档案 | 每份材料的当前状态和历史是什么？ | 查看版本或回到对应任务 |
| 报告页 | 哪些已通过材料可以装配成果？ | 预览或排队导出 |
| 教师首页 | 现在最需要我判断什么？ | 打开一个审核/认领/成员确认事项 |
| 教师项目详情 | 这个团队进度、风险和待办是什么？ | 处理一个指导事项 |
| 平台学校详情 | 这个学校授权是否正常、要变更什么？ | 确认一项授权变更 |

原实现的问题是将“概览、编辑、审核、历史”混在同一组件中，再通过 `route.meta.surface` 切换模板。这会造成内容重复、操作位置不稳定和页面标题与实际动作不一致。

### 3.2 交互反馈缺口

缺口分为四类：

1. **结果不可见**：点击后只有接口请求，没有页面内状态变化。
2. **过程不可见**：重复点击、等待、上传或异步任务没有明确进行态。
3. **失败不可执行**：只显示“失败”，没有原因、修复方法和重试入口。
4. **风险动作无确认**：停用授权、重置邀请码、撤回赛事或下架内容容易误触。

统一规则是“操作前说明限制 → 操作中禁用重复提交 → 成功后更新状态并给下一步 → 失败后保留输入并给重试”。

### 3.3 任务状态不直观

仅用百分比或绿色标签不能说明用户能否操作。任务必须同时表达四层信息：

- 状态文字：未解锁、可开始、编辑中、待审核、需修订、已通过、已完成。
- 视觉语义：颜色、图标和边框层级共同表达，不依赖颜色单独表达。
- 原因：未解锁要写清前置条件，需修订要显示教师意见摘要，待审核要写明提交时间。
- 行动：每张任务卡只允许一个主行动，文案必须与状态语义一致。

完成度也必须拆成“已通过任务数 / 总任务数 / 百分比 / 当前优先任务”，避免把待审核任务误算成完成。

### 3.4 页面重复与层级混乱

信息权威来源必须唯一：任务要求只在任务页，版本历史只在材料档案，项目总进度只在项目概览，今天的行动只在学生首页。其他页面只能显示摘要和进入入口，不能复制完整内容。

## 4. 已落地的交互改进

### 4.1 统一反馈层

已实现或接入：

- `frontend/src/components/FeedbackBanner.vue`：成功、失败、只读限制、下一步和重试。
- `frontend/src/components/ConfirmDialog.vue`：授权停用、邀请码重置、赛事发布/撤回等高风险动作。
- `frontend/src/stores/feedbackModel.ts`：统一反馈状态、语气和标题。
- `frontend/src/stores/interactionModel.ts`：统一认领、审核、成员、授权、赛事和搜索的成功文案。
- 顶栏通知与帮助入口不再是装饰按钮；品牌按钮返回当前角色首页。

### 4.2 学生任务闭环

- `StudentHome.vue` 只突出当前行动、修订优先级、项目进度、等待事项和一条 AI 建议。
- `TaskStatusCard.vue` 根据任务状态生成唯一主行动。
- `StudentTask.vue` 在提交前校验正文/附件和真实性确认；提交后进入待审核，打回后保留意见并进入修订状态。
- `studentApiModel.ts` 统一完成度计算和行动文案，已通过/已完成才计入完成度。
- 项目概览、地图、材料档案和报告页改为摘要/追溯/装配职责，不再全部显示同一份编辑信息。

### 4.3 教师与平台关键操作

- 教师认领、审核、成员确认具备进行态、成功和失败反馈。
- `TeacherProjectDetail.vue` 将团队、阶段、材料状态和风险放入一个指导工作台。
- 平台学校授权、邀请码、赛事状态变更具备确认弹窗和结果反馈。
- 内容库搜索执行真实过滤，并反馈结果数量或无结果原因。
- 平台设置页已接入脱敏的服务状态接口，仅显示数据库、队列、病毒扫描、文档转换、存储和 AI 的可用性，不返回密钥或密码。
- 项目成长记录已按“同一天只记一次经验/连续完成”修正，避免重复审核请求造成成长数据膨胀。

## 5. 尚未完成的工作与风险

下面内容不能以“页面能打开”视为完成：

### P0：必须补齐

1. **浏览器 E2E 基线**：登录/刷新/错误角色访问、学生提交→教师打回→学生重提→教师通过、平台停用授权三条链路需要自动化测试，而不是仅靠人工点击。
2. **所有写操作反馈统一化**：AI 中心、教师公告、公开案例申请、成员邀请和材料上传仍需逐项检查加载/成功/失败/重试/禁用状态。
3. **学生任务地图与任务页一致**：修订任务必须在首页、地图和教师队列中同时置顶；待审核不能继续显示“开始任务”。
4. **授权只读状态统一**：学校停用或到期后，所有写按钮必须禁用，并显示“仍可浏览历史内容，请联系平台管理员恢复授权”。

### P1：下一阶段

1. 将 `StudentProject.vue`、`TeacherWorkbench.vue`、`PlatformConsole.vue` 的大分支继续拆成独立路由组件和 Pinia store 模块。
2. 增加教师项目风险面板、团队成员管理、版本差异和最近活动。
3. 增加平台学校详情编辑、配额保存和审计记录；服务健康状态已完成首版，后续补充历史记录和告警策略。
4. 增加统一 `OperationToast`、`ProgressRail` 和更完整的 `EmptyState`，避免每个页面各写一套反馈。
5. AI 中心补齐服务状态、配额、失败重试和“预览→明确采用→写入草稿”的完整交互。

### P2：试点前保障

1. 真实上传进度、解析/OCR 状态、导出任务排队与重试。
2. 报告只装配最新已通过材料，公开案例使用材料白名单。
3. 键盘焦点、表单错误、图标按钮标签、对比度、1280/1440 宽度和窄屏溢出检查。
4. 依赖审计、备份恢复演练、跨校越权专项测试和试点操作手册。

## 6. 执行顺序与验收门槛

### 里程碑 M1：可信交互闭环

- 完成反馈组件、任务状态模型和学生唯一行动闭环。
- 完成教师审核、平台授权的确认与结果反馈。
- 前端测试、类型检查、构建、后端测试和迁移检查全绿。

### 里程碑 M2：三端职责清晰

- 每条路由对应明确页面职责，减少基于 `surface` 的大组件分支。
- 教师项目详情可在一个页面判断团队、进度、风险和待办。
- 平台学校详情可完成授权、邀请码和配额管理。

### 里程碑 M3：成果生产可追溯

- AI 生成、采用、提交、审核、报告装配和公开申请可回溯。
- 失败任务可重试，报告和案例不泄露未通过或未授权材料。

### 验收重点

- 用户在学生首页 5 秒内能看出唯一优先任务、当前状态和下一步结果。
- 每个提交、审核、启停、下架动作都有加载、成功、失败和必要确认。
- 已通过、待审核、需修订、未解锁在文字、图标、颜色和行动上都可区分。
- 任务地图、材料档案、项目概览不重复展示完整任务说明。
- 三端之间没有越权路由或职责混入，浏览器刷新和前进后退不会强制跳回学生端。

## 7. 当前判断

灵溯已经从“可展示的三端原型”进入“交互可信度和试点可用性打磨”阶段。核心任务状态和反馈基础已经落地，但在自动化 E2E、页面拆分、平台服务健康、AI 状态和材料/报告异步反馈完成前，不应宣称为生产级完成。后续开发按本文件的 P0 → P1 → P2 顺序推进，并在每个里程碑保留测试和浏览器验收证据。

## 8. 本轮继续落地与验证记录

### 8.1 已落地的补充改动

本轮在上述交互基础上继续处理了几个容易被忽略的断点：

- 学生新建项目成功反馈现在保存新项目 ID，点击“查看项目”不会误跳到项目列表中的第一个项目。
- 公开案例申请增加父页面成功反馈和重新加载申请历史；提交失败时保留表单输入，便于修订后重试。
- 平台设置从混合的运营大组件中拆出独立页面，加载服务状态时有读取态、失败态和重试入口。
- 平台运营组件不再监听不存在的 `watch` 依赖，避免进入平台路由时出现 Vue setup 异常。
- 服务状态接口已加入平台管理员权限检查，返回字段为非敏感状态词；教师请求得到 403，平台管理员可以读取。
- 旧演示项目在初始化脚本中会补齐缺失的任务地图和材料记录，避免首页出现“0/0”但项目实际应该可执行的空状态。

### 8.3 当前不能宣称完成的事项

以上验证证明的是首版交互闭环和容器运行正常，不等于生产级完成。仍需优先完成：

1. 自动化浏览器 E2E：登录/刷新、学生提交—教师打回—学生重提—教师通过、平台停用授权。
2. 材料真实上传进度、解析/OCR、报告导出排队/失败重试等异步状态。
3. 学生项目页、教师工作台和平台运营组件的进一步拆分，减少 `surface` 大分支带来的维护成本。
4. 跨学校越权、只读授权、附件下载、公开案例白名单和审计事件专项测试。
