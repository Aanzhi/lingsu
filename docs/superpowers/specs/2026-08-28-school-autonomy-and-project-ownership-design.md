# 灵溯学校自治、角色边界与项目归属设计

> 状态：待实现，已完成产品讨论稿
>
> 日期：2026-08-28
>
> 说明：本设计补充并覆盖既有方案中关于学校归属、教师权限、跨校项目和内容审核的规则。它不改变独立项目控制台的宿主机边界，也不把平台管理员变成学校教师。

## 1. 目标

灵溯由三个互相隔离的工作域组成：

1. 用户工作台：学生和教师使用，围绕学校、项目、研究和通知协作。
2. 平台端：面向平台管理员，跨学校管理业务数据、学校授权、账号、平台公开内容和系统配置。
3. 独立项目控制台：面向开发者，运行在宿主机上，只控制项目运行环境和服务生命周期。

本设计要解决四个核心问题：

- 学校是业务协作边界，但不建设单独的学校端。
- 教师没有等级差异，学校内部由教师共同承担管理责任。
- 学生升学后，第一作者可以携带同一个项目继续研究；前置学校只保留转移前的内容和记录。
- 平台不审核学校内部日常内容，只治理面向全网公开的内容和安全事件。

## 2. 已确认的产品原则

### 2.1 角色原则

- 用户角色只有学生和教师；教师代表学校，不新增学校管理员角色。
- 同一账号在同一时间只绑定一所当前学校，登录后直接进入该校工作台。
- 注册时用户自行选择学生或教师身份，学校邀请码只证明学校归属。
- 用户升学或换校时，可以使用新学校邀请码申请变更学校；平台确认后生效。
- 教师换校后立即失去旧学校全部访问权限，不能保留旧学校访问权限。
- 学生换校后仍可在个人历史项目中访问自己过去的项目，但这不等于恢复旧学校成员权限。
- 平台管理员可以有多个，彼此平权；平台管理员账号只能由初始化或开发者侧创建，不能公开注册。

### 2.2 教师平权原则

- 所有本校教师都可以查看本校项目、学生和学校通知，并执行学校级管理操作。
- 教师可以管理本校学生、项目和学校通知；所有学校级变更立即生效，不进入平台审核队列。
- 每个项目只有一名当前指导教师。
- 项目必须先进入本校项目池并由一名教师认领，才能开始研究；认领使用原子操作，不能重复认领。
- 认领后，只有当前指导教师拥有项目级材料写入、审核和状态变更权限；其他教师保留本校范围内查看权限。
- 项目完成/结题由第一作者发起、当前指导教师确认；不能绕过指导教师直接结题。
- 指导关系更换不能直接转交或改绑，必须由第一作者与当前指导教师确认解绑，项目重新入池，再由新指导教师认领。
- 指导关系更换不产生超级教师或学校管理员层级。

### 2.3 平台自治原则

- 平台端可以管理学校、教师、学生、项目、材料、公告、配额和账号状态，但“可以管理”不等于“逐条审核学校内容”。
- 学校内部项目、材料、教师批注和学校公告由学校自治，保存或发布后立即生效。
- 只有面向全平台或全网公开的内容才进入平台公开治理流程。
- 平台对学校内容只保留投诉、风险、数据泄露和法律合规场景下的冻结、下架、恢复能力；不得静默改写学校内容。
- 所有平台操作、学校内容变更、项目指导变更和跨校授权都要保留审计记录和版本历史。

## 3. 系统入口与边界

### 3.1 用户工作台

用户工作台包含公共入口、学生端和教师端：

- 公共入口：产品介绍、普通登录、注册和公开内容展示。
- 学生端：我的项目、研究过程、材料、灵思 AI、项目邀请、成果申请和通知中心。
- 教师端：工作台、项目池、指导项目、材料审核、学生管理、学校通知和公开展示申请。

用户工作台不出现开发者控制台入口。公告入口只面向登录后的学生和教师，使用“通知中心”表达用户任务和消息，不使用平台后台的管理语言。

### 3.2 平台端

平台端使用独立入口和独立登录页，例如 `/platform/login` 和 `/platform/*`。平台端负责：

- 学校创建、授权、停用和邀请码轮换；
- 教师和学生账号的新增、移除、停用、恢复和换校处理；
- 跨学校业务数据管理和问题处理；
- 平台 AI Agent 模板、平台赛事和平台公告；
- 全网公开案例的治理、发布、下架和恢复；
- 配额、安全策略和业务审计。

平台登录入口可以单独存在于普通登录或明确的管理入口中，但不得嵌入用户公告中心、学校通知页或学生/教师业务页面。

### 3.3 独立项目控制台

控制台继续由 `scripts/console.sh` 启动为宿主机进程，默认监听 `127.0.0.1:8800`。它不加入 Docker Compose，不使用学生、教师或平台业务角色，也不通过用户工作台导航暴露。

控制台只负责：

- Docker/Colima 状态；
- 前端、后端、数据库、队列等项目服务的启动、停止、重启；
- 服务健康检查、日志和 E2E 验收；
- 将启动中、停止中、运行中、已停止、异常等状态可视化。

控制台自身要显示“宿主机独立运行”、监听端口、PID 和最近状态变化。启动或停止项目服务不会启动或停止控制台进程。

## 4. 学校、账号与成员关系

### 4.1 学校创建

学校只能由平台端创建和授权。平台为学校生成邀请码，并可以停用、轮换或重新生成邀请码。

邀请码只负责学校绑定，不决定用户身份。注册者自行选择学生或教师；学校内部不设置首位教师、超级教师或学校端账号。

### 4.2 当前学校绑定

业务规则上，一个账号只有一个当前学校：

- `current_school` 是账号进入工作台、读取通知和执行业务操作的唯一上下文；
- 当前学校变更后，普通查询不能再通过旧学校筛选到该账号；
- 学校变更、角色变更、停用、恢复都要记录操作者、时间、旧值、新值和原因；
- 旧学校关系保留为审计历史，不等于保留访问权限。

学生与教师都可以因升学、转学或身份变化重新绑定新学校，并在新学校重新选择学生或教师身份。

### 4.3 学校状态

学校被停用或授权到期时：

- 学生和教师可以登录并查看历史内容；
- 用户端进入明确的只读维护状态；
- 禁止新建、编辑、审核、发布和使用 AI；
- 页面告知学校授权状态和联系平台的方式；
- 恢复授权后，正常业务能力恢复。

## 5. 项目归属与跨校迁移

这是本系统最重要的业务规则。项目归第一作者，不归学校。项目可以跟随第一作者更换当前学校和指导教师，但项目根作者、原始创建学校和历史记录不可被改写。

这里要区分两个学校属性：

- `origin_school`：项目最初创建学校，永久不变，用于成果归属和历史署名；
- `current_school`：项目当前协作学校，可以由第一作者随着换校显式变更。

学校是项目的研究协作环境，不是项目所有者。A 学校保留其阶段贡献和转移前记录，B 学校承接项目当前研究，但不能修改 A 阶段历史。

### 5.1 项目根身份

每个项目根记录永久绑定：

- 第一作者/项目创建者；
- 原始创建学校；
- 创建时间和原始项目编号；
- 原始成员、指导教师、材料版本和审核历史。

第一作者不可更换，原始创建学校不可更换。项目本身不复制、不克隆、不生成多个续研分支。

### 5.2 第一作者携带项目换校

第一作者换校后，使用新学校邀请码完成当前学校变更；指导教师更换必须经过“解绑—入池—认领”，不能直接改绑：

1. 第一作者发起学校或指导关系变更；
2. 第一作者和当前指导教师共同确认解绑；
3. 当前指导教师解绑，项目重新进入项目池；
4. 如果第一作者同时换到 B 学校，项目池上下文随当前学校切换到 B；
5. B 学校教师从项目池重新认领项目，成为当前指导教师；
6. 新教师认领后，项目恢复“研究中”，第一作者和新指导教师继续使用同一个项目。

当前指导教师确认的是“结束本次指导关系并解绑”，不是对项目所有权进行审批。教师不拥有项目，平台也不审核项目是否应该迁移；如果双方无法完成解绑，第一作者仍可创建完全空白的新项目。

### 5.3 换校期间和换校后的访问边界

项目进入解绑或换校流程后，在新教师认领前暂时只读，不能继续推进研究。

- 第一作者：可以查看完整项目历史；新指导教师认领后恢复完整项目权限；
- B 学校：项目进入 B 学校项目池后，所有本校教师可以查看并由其中一人认领；认领完成后获得当前项目协作权限；
- A 学校：项目转到 B 学校后，只能查看项目转移生效时间之前的内容、版本和审核记录，不能查看 B 学校阶段的新增内容；如果只是同校更换指导教师，仍按本校项目范围查看，但不能绕过认领直接操作；
- 原指导教师：解绑后不再拥有当前指导权限，只能按 A 学校的历史只读范围查看；换校后不保留旧学校的其他访问权限；
- 其他原成员：保留本人历史贡献和迁移前只读访问，不获得 B 学校当前编辑权限。

项目状态建议为：

```text
项目入池（A 学校）
  ↓ A 学校教师认领
研究中（A 学校）
  ↓ 第一作者与当前指导教师确认解绑
项目重新入池（A 学校）
  ↓ 第一作者换校，项目池上下文切换
项目重新入池（B 学校）
  ↓ B 学校教师认领
研究中（B 学校）
```

“A 学校阶段”和“B 学校阶段”通过学校关系历史和版本时间线表达，不创建新的项目编号，也不把 A 学校的项目改写成 B 学校原创项目。教师更换始终经过项目池，不能通过第一作者的直接邀请绕过认领。

### 5.4 历史审核与材料

项目不通过复制来同步历史记录，而是继续使用原项目版本链：

- A 阶段材料、审核结论、审核意见、指导教师和时间永久保留；
- B 学校可以查看继续研究所需的项目历史；
- A 学校的历史视图在迁移时间处截断，不能看到 B 阶段新增内容；
- B 阶段产生新的材料版本和审核事件，不覆盖 A 阶段记录；
- 原始记录保留来源学校和原指导教师，不能重新署名。

### 5.5 不携带项目时的新建项目

第一作者也可以选择不携带原项目，而在 B 学校创建一个完全空白的新项目：

- 不复制标题、研究问题、计划、附件、版本或审核记录；
- 不建立项目链关系；
- 这个项目是 B 学校的新根项目；
- 重新进入 B 学校项目池，由指导教师认领后，从零开始研究；
- 平台不审核、不阻止、不干涉学生重新立项。

学生可以保留原项目的个人历史查看和导出权限，但新项目不能利用复制流程带出原学校内部资料、教师批注或学校资源。

### 5.6 团队项目

- 第一作者是团队项目唯一可以携带项目换校的人；
- 非第一作者转学后，只能查看和导出迁移前的个人历史贡献，不能携带项目或创建分支；
- 第一作者换校后，项目当前协作权进入 B 学校；A 学校其他成员只保留迁移前只读范围；
- B 学校的成员必须重新满足 B 学校成员关系，不能自动把 A 学校成员带入当前协作空间；
- 第一作者不能删除其他成员的历史贡献记录。

### 5.7 项目回收站

- 项目删除只能由第一作者发起，不能直接永久删除；
- 删除操作先将项目移入回收站，保留 30 天，期间第一作者可以恢复；
- 进入回收站后停止研究、编辑、审核和公开申请等业务操作；
- 30 天后自动清理项目正文、附件、AI 对话和导出文件；审计系统只保留不可恢复的删除摘要、操作者、时间和项目原始标识。

## 6. 内容可见性与审核治理

### 6.1 三种内容范围

建议在业务模型中明确区分：

1. `school_internal`：本校内部内容，包括项目、材料、审核、学校公告。
2. `platform_user`：平台发布给登录用户的内容，包括平台公告、赛事和系统通知。
3. `network_public`：面向全网或公共入口的案例、成果和公开内容。

默认创建的学校内容必须是 `school_internal`，不得因为保存、复制或换校自动变为公开内容。

### 6.2 学校内部内容

- 所有教师可以管理本校公告和学校级信息，发布、编辑、撤回立即生效；
- 项目内容的写入和审核仍遵循当前指导教师的对象级权限；
- 不需要平台管理员事前批准；
- 变更自动形成版本和审计事件；
- 支持撤回、恢复和查看修改前后差异。

### 6.3 全网公开内容

只有以下动作进入平台公开治理：

- 学校或学生申请将项目作为公开案例展示；
- 内容从学校内部范围转为全平台/全网范围；
- 公开赛事、平台公告和公共案例的发布、下架与恢复。

公开案例应保留第一作者、原始学校、后续协作学校和各阶段指导贡献。学生同意、指导教师确认和平台公开发布是独立事件，不能用学校内部的即时发布规则替代。

### 6.4 平台例外处置

平台管理员可以在投诉、数据泄露、恶意内容、违法风险、病毒附件或服务安全事件下：

- 临时冻结内容；
- 隐藏或下架公开内容；
- 恢复错误下架的内容；
- 关闭异常账号或学校授权。

平台不得静默改写学校原始内容。例外处置必须记录原因、操作者、处置前状态、处置后状态和恢复条件。

## 7. 通知中心

公告和通知不再作为平台后台的公共入口展示，而是按用户工作逻辑组织：

- 学生和教师登录后进入统一“通知中心”；
- 学生看到本校通知、平台公告、项目邀请、审核结果和成果状态；
- 教师看到本校通知、平台公告、项目认领、待审核和成果申请；
- 内容显示来源标签，例如“本校”“平台”“项目”；
- 本校通知只按当前学校发送；
- 平台管理员和控制台入口不出现在通知中心；
- 未登录用户不进入学校通知中心。

平台公告如果需要面向公共访客展示，应使用独立的公共内容页面，不修改通知中心的用户定位。

## 8. 权限矩阵

| 能力 | 学生 | 教师 | 平台管理员 | 独立控制台 |
|---|---|---|---|---|
| 查看本校项目 | 参与项目范围 | 全校 | 全平台 | 无 |
| 创建新项目 | 可以 | 按产品规则处理，不作为学生创建者 | 可以管理 | 无 |
| 认领项目 | 无 | 未认领项目池 | 可处理异常 | 无 |
| 编辑项目材料 | 自己可编辑范围 | 当前指导教师 | 可管理和恢复 | 无 |
| 审核项目材料 | 无 | 当前指导教师 | 可管理，但不做日常前置审核 | 无 |
| 管理本校学生和公告 | 无 | 可以 | 可以跨校 | 无 |
| 携带项目换校 | 仅第一作者 | 当前教师共同确认解绑；新教师必须从项目池认领 | 只处理账号和异常状态 | 无 |
| 公开发布项目 | 发起申请/确认 | 确认或邀请 | 审核发布 | 无 |
| 管理学校授权 | 无 | 无 | 可以 | 无 |
| 控制项目服务 | 无 | 无 | 无 | 可以 |

平台管理员可以跨学校处理业务数据，但平台访问和写入都必须进入审计记录；平台管理员不成为项目指导教师，也不替代学校教师的日常指导职责。

## 9. 建议的数据模型调整

现有模型已经具备 `Account.school`、`Account.role`、`Project.school`、`Project.primary_teacher`、`Announcement.school` 和 `AuditEvent` 等基础能力，但不能只依靠当前的学校外键表达全部规则。

建议增量补充：

### 9.1 账号与学校

- `SchoolMembershipHistory`：记录账号的学校、身份、起止时间、变更原因和操作者；同一账号只能有一个当前有效关系。
- 当前学校继续作为业务查询上下文；旧关系只用于审计和学生个人历史项目访问。
- 学校邀请码独立为可轮换的邀请记录，支持失效时间、撤销和使用审计。

### 9.2 项目换校

- 项目保留唯一编号和第一作者；`origin_school` 永久不变，现有 `Project.school` 或等价字段表达 `current_school`。
- `ProjectSchoolHistory`：记录项目在每所学校的生效时间、结束时间、换校发起人和变更原因，用于截断原学校只读范围。
- `ProjectGuidanceHistory`：记录指导教师入池认领、解绑、重新认领和关系结束时间。
- `ProjectSchoolTransfer`：记录第一作者发起的换校、旧学校、目标学校、状态和生效时间；使用事务和唯一生效约束防止并发换校。
- 回收站记录：记录第一作者发起时间、恢复截止时间、最终清理时间和清理结果。
- 项目不创建续研克隆或跨校分支；第一作者选择不携带时，创建新项目且不关联旧项目。

### 9.3 内容范围

- 公告、案例和成果申请增加明确的可见范围和发布渠道字段；
- 学校内部内容不使用平台审核状态；
- 全网公开内容保留发布者、来源学校、贡献学校和公开审核记录；
- 版本和审计事件支持恢复，不删除原始学校记录。

## 10. API 与权限实施重点

1. 把“教师可查看本校所有项目”和“当前指导教师可写入/审核”拆成两个独立权限层。目前教师项目查询偏向只返回本人指导项目，需要调整为学校范围读取、对象范围写入。
2. 账号学校查询统一使用当前学校上下文；教师换校后所有旧学校接口必须拒绝访问。
3. 学生历史项目使用明确的“项目创建者/成员历史访问”路径，不放宽普通学校查询条件。
4. 第一作者换校和指导教师绑定采用显式状态机，并严格执行“入池—认领—解绑—重新入池—新指导教师认领”；使用事务和唯一约束防止并发换校或重复认领，学校关系历史按生效时间限制旧学校读取范围。
5. 第一作者选择重新立项时，创建新项目的接口只生成空白项目，不接受原项目 ID 或自动复制参数。
6. 项目删除接口只能把项目移入回收站；恢复和 30 天后的清理必须可审计，不能提供前端直接永久删除。
7. 公告接口按 `school_internal`、`platform_user` 和 `network_public` 分流，避免共享页面或接口误把学校公告当作公共内容。
8. 平台管理员的业务管理能力与平台内容审核能力分开；学校内容日常写入不产生平台待审状态。
9. 所有账号、学校、项目、公告和公开内容的管理操作统一写入审计事件。

## 11. 页面调整重点

### 学生端

- “我的项目”区分当前学校项目和个人历史项目；
- 历史项目显示原学校、原指导教师和访问权限说明；
- 第一作者在换校后看到“携带项目到新学校”入口；
- 项目换校后进入 B 学校项目池，显示“待新指导教师认领”，认领完成后恢复研究操作；
- 原学校只看到迁移前的只读内容和记录；
- 非第一作者只看到迁移前的历史项目和个人贡献导出；
- 第一作者选择重新立项时，提供明确的“创建空白新项目”入口；
- 新项目必须重新进入 B 学校项目池并由指导教师认领后才能进入研究流程；
- 删除项目时只显示“移入回收站”，并显示 30 天恢复倒计时。

### 教师端

- 项目池展示全校未认领项目；
- 指导项目展示本人负责项目；
- 本校项目详情允许全校教师查看，但非指导教师不显示编辑、审核和状态操作；
- 学校通知提供直接发布、编辑、撤回和版本恢复，不出现“等待平台审核”；
- 项目换校状态和指导教师绑定状态分别展示；原指导教师负责确认解绑，目标学校教师必须从项目池认领，不提供直接改绑或项目转移否决入口。

### 平台端

- 学校空间管理账号、学校授权、邀请码和异常处理；
- “公开内容治理”只展示平台公开内容和公开申请，不展示学校日常内容待审核队列；
- 业务数据管理、公开治理、审计和服务状态使用不同分区。

### 控制台

- 总览卡片明确区分“控制台自身”和“项目服务”；
- 启动、停止、重启显示状态过渡，不使用瞬时成功文案；
- 项目服务停止不会将控制台显示为停止；
- Docker/Colima 操作显示影响范围并要求确认。

## 12. 实施顺序

### 第一阶段：先完成权限和数据契约

- 增加项目学校历史、项目换校状态和指导关系记录；
- 梳理学校范围读取与对象范围写入；
- 拆分学校内部内容和平台公开内容；
- 补齐审计事件和版本恢复。

### 第二阶段：重做入口和页面表达

- 独立用户、平台和控制台入口；
- 用户通知中心与平台管理页面分离；
- 学生历史项目、项目换校、空白新项目和教师项目池；
- 平台公开内容治理页。

### 第三阶段：补齐状态和异常流程

- 换校、学校停用、指导教师解绑、项目入池和重新认领；
- 审核记录的学校阶段边界与历史访问；
- 团队项目成员跨校访问；
- 控制台服务启动/停止状态可视化。

### 第四阶段：测试与验收

- 后端权限矩阵测试；
- 学生、教师、平台端路由和导航测试；
- 项目换校单链、解绑后重新入池、空白新项目、历史访问和旧学校拒绝访问测试；
- 公告内部即时发布与公开内容审核测试；
- 控制台状态、启停和独立进程测试；
- 1280px/1440px 页面截图和全路由验收。

## 13. 非目标

- 不新增学校管理员或超级教师角色。
- 不把平台审核扩展到学校内部日常内容。
- 不允许项目第一作者和原始创建学校被静默修改；当前学校变化必须产生换校记录。
- 不允许复制或克隆同一项目形成跨校分支；项目只能由第一作者携带同一个编号继续。
- 不把平台登录或开发者控制台入口放进用户公告中心。
- 不把独立控制台嵌入 Vue 业务前端或 Docker Compose。
