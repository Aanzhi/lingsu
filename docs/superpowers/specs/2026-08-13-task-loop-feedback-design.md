# 灵溯任务闭环与交互反馈设计规范

## 背景与目标

当前三端页面已经具备项目、任务、材料和审核的基本能力，但用户体验存在三个结构性问题：操作后反馈不足、任务完成状态缺少层次、概览/任务/材料页面重复表达同一信息。

本规范以第一性原理重新定义页面：每个页面只帮助用户完成一类决策或一项操作。平台的核心体验不是“浏览很多页面”，而是推动真实科创项目完成以下闭环：

```text
看见下一步 → 开始任务 → 提交证据 → 获得审核反馈 → 解锁下一步
```

目标是让学生始终知道“我现在该做什么、我为什么不能继续、我做完后会发生什么”；让教师始终知道“我现在要审核什么、哪个项目有风险”；让平台管理员始终知道“哪些学校和内容需要治理”。

## 统一交互原则

### 一页一个主要问题

| 页面类型 | 只回答的问题 | 不承担的职责 |
| --- | --- | --- |
| 首页 | 我现在最应该做什么？ | 不编辑完整项目，不展示全部历史材料。 |
| 项目概览 | 项目整体走到哪里、谁参与、有什么风险？ | 不承担具体材料编辑。 |
| 任务页 | 如何完成这一项任务并提交证据？ | 不展示全部项目档案。 |
| 材料档案 | 每项材料当前状态和历史版本是什么？ | 不重复任务说明和行动引导。 |
| 报告页 | 哪些已通过材料能装配成成果？ | 不处理日常任务。 |

同一信息只保留一个权威来源：任务要求在任务页，材料版本在材料档案，项目总进度在项目概览，今天行动在首页。

### 操作必须有可见结果

所有创建、保存、提交、审核、启停、下架操作遵循一致的四段反馈：

1. **操作前**：说明结果与限制；高风险动作使用确认弹窗。
2. **操作中**：按钮进入加载态并禁用重复提交；上传显示逐文件进度。
3. **成功后**：出现成功提示，页面状态立即更新，并给出下一步入口。
4. **失败后**：显示明确原因、可执行处理方法和重试入口，绝不只显示“操作失败”。

成功反馈采用顶部轻量提示 + 页面内状态变化的双层形式。例如材料提交成功后：顶部提示“已提交给王老师审核”；任务页变为“待审核”；主操作变为“查看提交版本”；同时显示“审核通过后将解锁：研究设计”。

## 任务状态系统

### 状态定义

| 状态 | 用户含义 | 主视觉 | 主操作 |
| --- | --- | --- | --- |
| 未解锁 | 尚不需要做；必须先满足前置条件。 | 浅灰、锁图标、写明解锁条件。 | 查看解锁条件。 |
| 可开始 | 当前最值得完成的任务。 | 苔藓绿高亮、编号、主按钮。 | 开始任务。 |
| 编辑中 | 已开始但未提交。 | 中性纸张色、保存时间、进度条。 | 继续编辑。 |
| 待审核 | 已提交，学生暂时无需重复操作。 | 灰蓝色、时钟图标、提交时间。 | 查看提交版本。 |
| 需修订 | 教师需要学生优先处理的任务。 | 陶土红、置顶、教师意见摘要。 | 查看反馈并修订。 |
| 已通过 | 证据被认可，可以进入下一步。 | 深绿色、勾选图标、已获得 XP。 | 查看成果。 |
| 已完成 | 任务及其必需材料都已完成。 | 低饱和绿色、完成日期。 | 查看成果。 |

颜色不能单独表达状态：所有状态同时必须有文字、图标和明确行动语句。

### 状态层级规则

学生首页和项目任务地图固定按以下优先级显示：

1. 需修订任务。
2. 当前可开始/编辑中任务。
3. 待审核任务。
4. 已通过任务。
5. 未解锁任务。

当前任务只允许存在一个主行动入口。若存在修订任务，它替代普通“下一任务”；若没有可用任务且有待审核材料，首页明确说明正在等待审核，而不是继续显示无法执行的按钮。

## 学生端信息架构

### 学生首页：今天的行动台

首页只保留五个区块：

1. **当前行动卡**：唯一主任务、状态、预计完成时间、主按钮。
2. **修订优先卡**：仅存在需要修订时出现，展示教师可执行意见。
3. **项目进度条**：阶段完成度、已通过材料数、下一阶段解锁条件。
4. **等待与提醒**：待审核状态、赛事截止、未读公告。
5. **AI 建议**：只显示与当前任务相关的一条建议，进入完整 AI 思考室。

首页不显示完整成员列表、完整材料列表、全部案例或大量重复项目介绍。

### 项目概览：项目的地图而非第二个首页

项目概览负责展示题目、研究问题、项目类型、成员、主指导教师、阶段完成度、近期活动和风险。它不提供完整材料编辑表单，也不重复首页的“今天任务”。

阶段区域以五段进度呈现，每段给出：阶段名称、完成数量/总数、状态、一个进入任务地图的入口。具体任务只在任务地图展示。

### 任务地图：可理解的研究路径

任务地图展示完整旅程，但只突出当前阶段与下一项可行动任务。已完成阶段折叠为摘要；未来阶段显示解锁条件；需修订的任务使用独立修复标记并始终优先。

地图上的卡片只展示任务名称、状态、证据数量、预计耗时和奖励。任务说明、教师反馈全文、材料正文不放在地图上。

### 任务页：唯一提交场所

任务页由四个固定区域组成：

1. **任务头部**：当前状态、完成目标、通过后将解锁什么。
2. **证据清单**：必需材料、允许格式、是否已完成、截止时间。
3. **工作区**：文本草稿、附件、AI 辅导、真实性确认。
4. **结果区**：提交后展示审核时间、教师意见、当前版本和修订入口。

任务不再使用“接取”这一不准确表述。若尚未开始使用“开始任务”；有草稿时使用“继续编辑”；提交后使用“查看提交版本”；被打回时使用“根据反馈修订”。

### 材料档案与报告

材料档案是只读追溯视图，按状态和报告章节分组。每条材料显示版本数量、最近修改人、最近审核结果和进入对应任务的链接。

报告页只显示已通过材料、章节完整度、缺失章节和导出历史。未通过、待审核、需修订材料绝不混入正式报告完成度。

## 教师端信息架构

教师首页按“需要判断的事情”组织，而非按学生页面复刻：

1. 待审核材料：数量、最久等待时间、按修订任务优先。
2. 待认领项目：题目、问题、项目类型、创建时间。
3. 待确认成员：邀请人、被邀请人、所属项目。
4. 指导项目风险：逾期、连续被打回、长时间待审核、阶段停滞。

教师项目详情是指导工作台，必须同时呈现成员、阶段、任务状态、材料审核历史、逾期风险和最近活动。它不重复教师首页的审核收件箱，也不显示学生等级面板。

审核页只聚焦一个材料版本：证据、版本差异、AI 审核摘要、通过或打回。打回动作必须填写意见，成功后马上从队列移除并显示“已通知学生”。

## 平台端信息架构

平台端只处理学校授权、全局赛事/公告、公开案例治理和服务状态。

学校详情必须将授权状态、到期日、邀请码、AI 配额、存储配额和使用概览置于同一工作台；每项可变配置有保存、确认、成功和审计反馈。平台端不展示项目任务地图、材料编辑器或教师审核收件箱。

平台设置必须展示服务是否可用，而不显示密钥：AI、后台任务、病毒扫描、文档转换、对象存储和数据库的状态应可见。

## 通用组件规范

所有三端统一使用以下反馈组件：

- `FeedbackBanner`：页面内成功、失败、只读限制和下一步提示。
- `OperationToast`：非阻塞的操作成功或失败反馈。
- `ConfirmDialog`：停用授权、重置邀请码、下架内容、删除/撤销等不可逆或影响他人的操作。
- `TaskStatusCard`：任务状态、行动、解锁条件与反馈的统一载体。
- `ProgressRail`：阶段完成度、当前阶段和下一阶段条件。
- `EmptyState`：解释为什么为空，并提供唯一合理的下一步。

顶栏的品牌、通知、帮助必须是实际入口；如果功能尚未实现，应暂时隐藏，不能保留无响应控件。

## 错误与只读限制

当学校被停用或过期时，用户可读取历史内容，但所有会改变状态的控件应直接呈现为禁用状态，并显示固定解释：

> 学校授权当前不可写入。你仍可浏览已有项目和材料；请联系平台管理员恢复授权。

表单错误必须靠近字段显示，提交错误必须保留用户已填写内容。网络错误保留重试按钮；AI 未配置时不展示可点击的“生成”，而显示服务状态和管理员处理提示。

## 验收标准

1. 学生在首页 5 秒内能辨认当前唯一优先任务、当前状态和下一步结果。
2. 每个提交、审核、启停、下架操作均有加载、成功、失败和必要确认状态。
3. 学生不会在项目概览、任务地图、材料档案中看到重复的完整任务说明。
4. 修订任务在首页、任务地图和教师队列中均优先于普通任务。
5. 已通过、待审核、需修订、未解锁在文字、图标、颜色和可行动作上均可区分。
6. 教师项目详情能够在不返回列表的情况下判断团队、进度、风险和待办。
7. 平台管理员能在学校详情完成授权配置，并获得明确的保存与审计反馈。
8. 1280px 和 1440px 桌面宽度下没有横向溢出；窄屏时重要证据要求重新排版，不能直接消失。
