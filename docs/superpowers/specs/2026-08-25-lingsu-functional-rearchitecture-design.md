# 灵溯全站功能重梳理与 UI 实施设计

> 状态：已确认的产品设计基线
>
> 日期：2026-08-25

## 1. 目标与系统边界

灵溯是面向学校的青少年科学创新项目工作台，负责把学生的课题想法组织成可研究、可审核、可沉淀和可展示的项目成果。系统由四个业务入口和一个独立控制平面组成：

- 公共入口：产品 Hero、登录注册、公开优秀案例、赛事公告和简易使用指引。
- 学生端：学生创建/加入项目、研究旅程、材料与实验日志、灵思 AI、邀请、成果申请和通知。
- 教师端：学校项目池、项目认领、指导项目、材料审核、学生管理、展示申请和学校内容。
- 平台端：学校空间、平台 AI Agent 模板、赛事公告、案例治理和系统设置。
- 项目控制台：独立于业务端和 Docker 项目的本机控制平面，控制服务生命周期、读取日志和运行健康验收。

控制台由独立启动脚本运行，监听本机地址；项目服务或 Docker 停止、重启时控制台进程必须继续运行。控制台不使用学生、教师或平台业务权限，也不暴露到公共入口。

PC 端最低支持宽度为 1280px，1440px 为主要视觉验收基线，不建设移动端布局。

## 2. 角色与核心对象

### 角色规则

- 学生全部平权：学生可以创建多个项目，也可以作为成员加入其他项目；每个学生设置一个当前项目，Hero 和研究/答辩 AI 默认使用该项目。
- 教师全部平权：教师共享本校项目统计和项目池；只有项目指导教师可以查看和处理该项目的材料审核。
- 平台管理员负责跨学校治理、公开内容和服务配置，不介入学校日常研究审核。
- 公共用户只能读取已发布的公域案例、平台赛事和公共公告。

### 核心对象

`School`、`Account`、`Project`、`ProjectMember`、`ProjectTask`、`Material`、`MaterialRevision`、`MaterialAttachment`、`Template/TemplateStage/TemplateTask/TemplateMaterial`、`AIConversation/AIConversationMessage/AIGenerationLog`、`AgentTemplate`、`MemberInvitation`、`PublicCaseRequest`、`Competition`、`Announcement` 和 `Notification` 共同组成业务模型。

项目是所有研究流程的根对象；步骤定义研究旅程；材料和实验日志是步骤证据；审核版本记录学生修改和教师意见；AI 会话产生草稿但默认不直接写入项目业务数据；成果申请将完成项目转为校内或平台公域展示内容。

## 3. 信息架构与页面职责

### 公共入口

公共入口使用全屏布局，不显示左侧栏和 Demo 提示。页面包括：

- Hero 首页：产品价值、简单指引、登录/注册和优秀案例入口。
- 普通登录、注册、平台独立登录：普通账号和平台账号入口隔离。
- 优秀案例列表与详情：只展示平台审核通过并发布的公域案例。
- 赛事和公共公告：展示平台发布内容。

已登录用户从公共入口进入对应角色工作台。

### 学生端

学生端使用全屏 Hero + 顶部导航，导航入口为：

- 首页：当前项目、项目进度、下一步任务、最近材料、审核反馈、赛事和学校通知。
- 我的项目：项目列表、当前项目切换、直接填写开题报告创建项目、AI 引导开题、项目详情、归档和回收站。
- 研究旅程：章节、步骤、模板预览/下载、材料上传、实验日志、步骤状态、审核意见和开始制作信息。
- 材料档案：已完成步骤、材料文字、附件、版本和审核记录。
- 灵思 AI：开题、研究、答辩三大类及其 Agent。
- 项目邀请：邀请同学、接受同学或教师邀请、查看成员变更记录。
- 成果申请：学生发起的校内展示申请、教师公域展示邀请的确认。
- 赛事与通知：平台赛事、公共公告、学校通知和系统通知。

项目创建有两条入口：

1. 学生已有方向时，直接填写结构化开题报告，确认后创建项目。
2. 学生没有方向时，进入开题 AI 工作台，完成引导后预览开题报告，确认后创建项目。

项目创建后生成当前模板快照和初始研究步骤，进入待认领状态。

### 教师端

教师端使用方案 B 的管理侧栏，包括：

- 工作台：本校项目状态、活跃度、待认领项目和本人待审核数量。
- 项目池：全校新建项目，默认按待认领展示；可查看开题细则并认领。
- 指导项目：本人负责项目的进度、成员、材料和研究状态。
- 材料审核：只展示本人负责项目的待审核材料；支持通过、打回修改和建议。
- 学生管理：本校学生资料、项目参与和成员状态。
- 项目邀请：邀请或调整项目学生成员。
- 成果申请：处理学生校内展示申请，向完成项目发起全平台展示邀请。
- 赛事公告和学校通知：查看平台内容并发布校内通知。

项目池认领使用原子操作，同一项目只能有一个指导教师；其他教师仍可查看学校统计和项目池，但不能处理该项目审核。

### 平台端

平台端使用方案 B 的管理侧栏，包括：

- 平台概览：学校空间、项目活跃度、公开案例状态、AI 使用量和服务健康。
- 学校空间：学校列表和详情；学校名称进入详情，授权开关只负责启停授权。
- AI Agent 模板：管理名称、角色、分组、适用端、上下文范围、启用状态和排序。
- 赛事与公告：发布平台赛事和公共公告。
- 案例管理：查看、编辑、审核、发布、下架和驳回公开案例。
- 系统设置：安全策略、AI 可用性和服务健康。

### 独立项目控制台

控制台页面包括：

- 总览：项目整体状态、Docker/Colima、前端、后端和任务服务指标。
- 服务明细：单服务状态、启动命令和最近状态变化。
- 控制操作：启动、停止、重启整个项目或单个服务；Docker/Colima 单独控制。
- 日志：按服务读取最近日志，支持错误日志定位。
- 健康验收：服务健康、接口检查、E2E 验收和最近结果。

停止或重启 Docker、Colima 或整个项目时必须二次确认；控制台自身不可被这些操作停止。

## 4. 灵思 AI 工作台

### 交互结构

采用 WorkBuddy 的交互构图，但保留灵溯方案 B 的浅色设计系统：

- 顶部为“开题 / 研究 / 答辩”三类切换。
- 分类下显示可用 Agent 标签。
- 中心区域为大对话框和聊天消息流，支持快捷提示、连续追问和历史会话。
- 项目名称、读取材料数、上下文范围和输出权限放在顶部控制区或抽屉。
- 输入框支持引用项目材料和调用 Agent；发送、生成、重试、复制和保存均有明确状态。
- 输出展示来源材料、结论、待确认项和可执行操作。

### 分类与上下文

- 开题：不绑定项目；负责选题、问题定义、研究目标、方法、计划、预期成果和开题报告。
- 研究：默认绑定当前项目；包含研究设计、资料分析、实验设计、实验日志、材料完善、数据整理和科创 Agent。
- 答辩：默认绑定当前项目；包含报告整理、答辩提纲、演示稿、问答模拟、成果展示优化和科创 Agent。

除开题外，AI 只能读取当前项目的材料、附件提取文字、实验日志、审核意见、成员信息和已确认内容，不能跨项目读取。

### 写入规则

AI 默认只保存会话、消息和生成草稿，不静默写入材料、项目状态、审核状态或公开内容。用户明确操作后才允许：

- 将草稿保存为某个步骤的材料版本。
- 将实验日志草稿保存为指定实验步骤的日志材料。
- 用完成的开题报告创建新项目。
- 将成果/答辩草稿带入成果申请表单。

教师侧 AI 只生成本人负责项目的审核建议；通过、打回、提交审核和发布必须由教师或平台管理员明确点击。

## 5. 状态机与业务规则

### 项目状态

项目主流程为：

`开题草稿 → 待认领 → 制作中 → 已完成`

项目可以从制作中或已完成进入归档，也可以从任意可删除状态进入回收站：

- 归档：长期保留，默认从工作区隐藏，可恢复。
- 回收站：保留 30 天，支持恢复；期满清理材料附件、AI 会话、导出文件和关联业务记录。
- 清理后保留不可恢复的审计摘要，不恢复业务内容。

### 研究步骤

`未开始 → 制作中 → 待审核 → 需修改 / 已通过 → 已完成`

每个实验相关步骤必须关联一份步骤级实验日志。系统在提交审核前检查必填材料和实验日志，不完整时阻止提交并指出缺失项。

### 材料版本

`草稿 → 已提交 → 审核中 → 需修改 / 已通过`

打回修改必须带有教师建议；学生修改创建新版本，旧版本只读保留。所有状态变更记录操作者、时间、原因和关联版本。

### 成果展示

- 学生发起的展示申请范围固定为校内，交由指导教师处理。
- 教师发起的全平台展示邀请必须由学生明确同意。
- 学生同意后进入平台案例审核；平台审核通过才发布到公共入口。
- 平台可以编辑、驳回、发布或下架，并保留审核记录。

## 6. 权限与通知

### 权限

- 学生只能查看自己的资料、自己创建的项目和加入的项目。
- 教师可查看本校共享统计和项目池；只有指导教师拥有项目材料审核写权限。
- 平台管理员拥有全平台配置、学校授权、Agent 模板、公共内容和服务状态权限。
- 公共用户只读已发布公域案例、平台赛事和公共公告。
- 控制台权限由本机运行边界决定，不接入业务角色权限。

### 通知

统一通知中心承载邀请、项目认领、材料审核结果、修改建议、成果状态、学校通知、平台公告和系统告警，支持未读、已读、全部已读和按类型筛选。

学校通知只发送给本校学生和教师；平台赛事和公共公告可以被公共入口和业务端读取；涉及成员、审核和成果申请的通知按接收人生成。

## 7. 数据/API 实施边界

优先复用现有 Django/DRF 数据模型和接口，不因 UI 重设计改动核心业务模型。仅在以下能力不足时补充字段、校验、接口或定时任务：

1. 当前项目设置和校验：确保当前项目属于当前学生可访问范围。
2. AI 分类与上下文：Agent 分类固定为开题、研究、答辩；每次生成记录项目范围、引用来源和输出草稿。
3. 显式保存：增加保存材料、保存实验日志和完成开题创建项目的明确动作接口。
4. 实验日志校验：模板材料标记为步骤级必填，并在提交审核时强校验。
5. 成果同意链：记录学生申请、教师邀请、学生同意、教师处理和平台审核状态。
6. 回收站清理：增加 30 天到期的后台清理任务、审计摘要和失败重试。
7. 通知类型：覆盖学校通知、平台公告、邀请、审核、成果申请和系统告警。

文件继续使用私有上传、病毒扫描、文字提取和导出流程；AI 只能通过后端授权上下文读取，不直接读取前端本地文件。

## 8. UI 实施策略

先完成全站 UI 设计，再接入实际业务：

1. 冻结本设计中的角色、页面、状态机和权限。
2. 使用确定性 fixture/ViewModel 完成全部路由的视觉和交互状态，不写入真实业务。
3. 建立共享组件：公共全屏壳、学生顶部导航壳、教师/平台管理壳、AI 中心对话框、项目状态、研究步骤、材料卡片、审核面板、邀请、成果申请、通知和空/错/加载状态。
4. 统一方案 B 字体、颜色、按钮、卡片、边框、圆角、间距和反馈；页面级 CSS 只负责业务网格。
5. 通过 1280px 和 1440px 截图矩阵后，逐端替换 fixture 为真实 API。
6. 最后补齐真实 loading、empty、error、disabled、无权限、上传扫描、AI 生成失败和写操作反馈。

## 9. 验收标准

- 公共入口全屏，无左侧栏、无 Demo 提示；学生端为全屏 Hero + 顶部导航；教师/平台端保持方案 B 管理壳。
- 所有页面使用同一套字体、按钮、卡片、状态、圆角、边框、阴影和间距。
- 学生可直接用开题报告创建项目，也可通过开题 AI 完成后确认创建；AI 不会静默写业务。
- 研究/答辩 AI 始终绑定当前项目且不能读取其他项目；教师 AI 只读取本人负责项目。
- 实验相关步骤没有必填日志时不能提交审核；教师打回必须保留建议和版本记录。
- 项目池认领不可重复；非指导教师不能处理该项目材料审核。
- 学生校内展示、教师公域邀请、学生同意和平台案例审核链路可完整跑通。
- 回收站项目 30 天内可恢复，期满清理业务文件并保留审计摘要。
- 控制台独立脚本可启动；项目/Docker 停止或重启不影响控制台；状态、日志和健康验收可用。
- 运行前端单元测试、全路由 Playwright、后端测试、控制台测试、构建和 1280/1440 截图差异检查。

## 10. 明确不在本轮范围

- 不建设移动端布局。
- 不因 UI 重设计更换数据库、重写核心业务模型或改变角色定义。
- 不让 AI 自动提交审核、自动发布案例或未经确认修改业务材料。
- 不把控制台嵌入业务前端或 Docker 项目。
- 不在全站 UI 未完成视觉验收前批量进入真实业务接入。
