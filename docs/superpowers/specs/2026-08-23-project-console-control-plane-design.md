# 灵溯项目控制台运行控制面设计

日期：2026-08-23  
状态：设计已确认，待实施计划  
范围：本机开发环境的项目运行控制、诊断、修复与验收

## 1. 目标与边界

灵溯项目控制台不是一个状态展示页，而是项目的本机运行控制面。它必须能够发现运行问题、解释问题、执行受控修复，并在修复后用真实登录链路重新验收。

控制台始终由宿主机独立进程运行，绑定 `127.0.0.1:8800`，不加入 Docker Compose，也不随 Docker/Colima 停止。控制台只能从本机访问，不提供局域网或公网控制能力。

保持不变：

- 不改变学生、教师、平台业务 API、数据库结构、权限逻辑和公开路由。
- 不把控制台加入 Docker 服务，不允许 Docker 启停控制台进程。
- 不提供任意 Shell 执行，只调用项目白名单动作。
- 不在日志、状态或浏览器页面中展示 API Key、密码、Cookie、Token 或完整环境变量。
- Demo 登录只用于开发交互，不计入真实登录验收。

## 2. 当前问题与根因

当前真实登录失败的根因是运行拓扑没有被统一管理：宿主机 Vite 的 `5173` 代理到了 `8001`，而被代理的 Django 进程只信任 `5175` 来源，导致 Django 在认证之前以 CSRF 来源校验失败返回 HTTP 403。

现有主 E2E 使用 `/api/demo-login/`，该接口绕过真实用户名/密码登录，因此主 E2E 通过不能证明 `/api/login/` 正常。控制台登录验收使用真实登录，但没有把 Vite 代理目标、后端监听端口和 `CSRF_TRUSTED_ORIGINS` 建模为同一个运行契约，也没有在启动前阻断配置漂移。

后续必须满足：

1. 启动前检查真实运行拓扑，而不是只检查端口是否有响应。
2. 真实 `/api/login/` 失败时，所有验收状态必须失败或阻塞。
3. 配置不一致必须显示证据，并提供受控修复路径。
4. 修复后必须重新执行健康检查和真实登录，不能沿用旧的通过结果。

## 3. 运行拓扑与运行契约

### 3.1 支持的运行模式

控制台支持两种明确模式，不能混用：

- Docker 前端模式：前端 Compose 服务监听宿主 `5173`，容器内代理目标固定为 `http://backend:8000`；后端宿主映射端口由 `BACKEND_BIND` 解析，例如 `18001`。
- 宿主机前端模式：前端由控制台启动的宿主进程监听 `5173`，启动时显式注入代理目标 `http://127.0.0.1:<BACKEND_PORT>`；不能继承来源不明的旧 `VITE_API_PROXY_TARGET`。

同一时间只能有一个灵溯前端占用 `5173`。控制台发现端口已被占用时，必须识别进程的工作目录和启动命令：只有确认属于当前项目的残留进程才允许清理；陌生进程只报告冲突，不自动终止。

### 3.2 运行契约字段

诊断引擎统一生成运行契约，至少包含：

- 控制台监听地址、PID 和独立性状态。
- 前端监听地址、端口、进程/容器身份、运行模式和实际代理目标。
- 后端监听地址、端口、进程/容器身份和健康检查地址。
- Compose 项目名、profile、服务清单和每个服务的容器状态。
- `CORS_ALLOWED_ORIGINS` 与 `CSRF_TRUSTED_ORIGINS` 中实际允许的前端来源摘要。
- Docker/Colima 可用性。
- 数据库、Redis、文件扫描、文档转换和 AI 服务状态。
- 最近一次真实登录验收、完整验收和修复操作结果。

契约校验必须明确区分“配置声明”和“实际运行”：只读 `.env` 不能替代读取实际进程命令、进程环境、Compose 配置和端口监听状态。

### 3.3 端口和来源校验

对本机开发入口默认校验：

- `http://127.0.0.1:5173`
- `http://localhost:5173`

后端可信来源必须覆盖实际使用的前端来源。若前端代理目标、后端端口或可信来源不一致，控制台显示“配置不一致”，阻断真实登录验收，并给出类似以下证据：

```text
frontend:5173 -> backend:8001
trusted origins: http://127.0.0.1:5175
required origin: http://127.0.0.1:5173
```

## 4. 控制台功能结构

### 4.1 顶部运行总览

页面首屏固定显示：

- 控制台自身：宿主机独立运行、PID、访问地址。
- 一键启动项目。
- 一键停止项目。
- 一键重启项目。
- 完整验收。
- 查看诊断与错误中心。
- 当前整体状态：未启动、启动中、运行中、存在问题、验收失败或停止中。

控制台自身永远不出现在项目服务计数中，但必须单独显示“控制台仍可用”。

### 4.2 服务与数据监控

按层级展示：

1. Colima/Docker 运行时。
2. PostgreSQL、Redis、ClamAV、Gotenberg。
3. Django、Celery、Celery Beat。
4. 前端进程或前端容器。
5. API 健康检查、真实登录、关键页面访问和最近验收。

每个服务提供状态、端口/容器、最近错误、最近日志和单服务启停入口。单服务操作仍必须经过白名单校验，并在依赖受影响时明确提示。

### 4.3 错误中心

错误中心使用本机 JSONL 事件记录，保留最近 7 天，文件位于项目本地运行目录并加入 Git 忽略。每条记录包含：

- `event_id`、时间、操作编号。
- 来源：console、frontend、backend、docker、colima、database、redis、ai、e2e。
- 等级：info、warning、error、blocked。
- 稳定错误代码。
- 用户可读标题与原因。
- 脱敏后的原始证据。
- 影响范围。
- 推荐修复动作。
- 修复前后状态。

首批稳定错误代码包括：

- `RUNTIME_DOCKER_UNAVAILABLE`
- `RUNTIME_PORT_CONFLICT`
- `RUNTIME_FRONTEND_PROXY_MISMATCH`
- `RUNTIME_BACKEND_PORT_MISMATCH`
- `RUNTIME_CSRF_ORIGIN_MISMATCH`
- `RUNTIME_CORS_ORIGIN_MISMATCH`
- `RUNTIME_STALE_PROJECT_PROCESS`
- `AUTH_DEMO_ACCOUNT_UNREADY`
- `AUTH_REAL_LOGIN_FAILED`
- `SERVICE_HEALTH_TIMEOUT`
- `SERVICE_CONTAINER_EXITED`
- `CHECK_BUILD_FAILED`
- `CHECK_TEST_FAILED`
- `CHECK_E2E_FAILED`

错误中心支持按等级、来源、操作编号和时间筛选，支持展开证据与日志，不直接显示敏感请求头或密码。

### 4.4 日志查看

日志来源白名单为：

- Compose 服务日志。
- 宿主机前端日志。
- 控制台操作日志。
- 诊断事件日志。
- 真实登录验收输出。
- 完整验收输出。

页面默认展示最近日志，支持按服务切换、刷新和复制脱敏文本。长日志只在日志区域内部滚动，不造成文档级横向溢出。

## 5. 操作与进度状态机

### 5.1 操作类型

- `start_project`
- `stop_project`
- `restart_project`
- `diagnose`
- `repair_runtime`
- `run_checks`
- 单服务 `start/stop/restart`
- `start_colima/stop_colima/restart_colima`
- `seed_demo`

每次操作生成唯一 `operation_id`，状态写入本机运行目录，浏览器刷新后可恢复最近操作。

### 5.2 一键启动

启动步骤固定为：

1. 检查控制台自身和操作锁。
2. 检查 Colima/Docker；必要时启动 Colima。
3. 检查 Compose 项目和依赖服务。
4. 启动 PostgreSQL、Redis、ClamAV、Gotenberg。
5. 启动 Django、Celery、Celery Beat。
6. 等待后端健康检查和依赖健康状态。
7. 启动正确模式的前端，校验端口、进程身份和代理目标。
8. 校验 CORS/CSRF 来源与实际前端入口。
9. 执行真实 `/api/login/` 登录验收，并检查登录后的首页访问。
10. 输出项目访问地址、服务摘要和可选的完整验收入口。

配置不一致时在第 7 或第 8 步暂停，不隐式修改文件；用户确认“修复并继续”后执行白名单修复并从失败步骤继续。

### 5.3 一键停止

停止顺序固定为：

1. 停止前端容器或受控宿主机前端进程。
2. 停止 Django、Celery、Celery Beat 和 Compose 依赖服务。
3. 保留 Docker/Colima。
4. 保留控制台进程。
5. 输出数据卷保留说明和停止结果。

停止或重启 Docker/Colima 是独立动作，必须二次确认，并明确可能影响本机其他容器。

### 5.4 状态与进度

步骤状态为：

```text
pending -> running -> succeeded
                  -> failed
                  -> waiting_confirmation
                  -> skipped
```

UI 展示百分比、当前步骤、已完成步骤、等待原因、重试次数、耗时和实时日志。健康检查可按明确上限重试；超过上限后进入失败，不无限等待。

## 6. 受控修复

### 6.1 允许的修复动作

- 根据当前运行契约同步前端代理目标。
- 补齐或校正本机前端来源的 CORS/CSRF 白名单。
- 生成配置备份并显示差异。
- 重启受影响的前端或后端服务。
- 清理确认属于当前项目目录的残留进程。
- 初始化/刷新演示账号和演示数据。
- 重跑服务健康检查和真实登录验收。
- 查看并重试失败的完整验收步骤。

### 6.2 安全规则

- 不修改密码、API Key、数据库密码和其他敏感字段。
- 不执行任意命令参数；所有动作映射到固定函数和固定参数集合。
- 停止、重启、清理进程、修改配置和初始化数据都需要明确确认。
- 配置修改前生成时间戳备份，修改后重新读取实际进程/容器配置。
- 陌生端口进程只报告，不自动杀掉。
- 修复过程、备份路径、差异摘要、返回码和重新验收结果全部写入操作历史。

## 7. 内部接口约定

继续使用本机控制台 HTTP API，并扩展为操作资源：

- `GET /api/status`：当前运行契约、服务摘要、错误摘要和当前操作。
- `GET /api/diagnostics`：完整诊断结果和错误代码。
- `GET /api/errors`：按时间、来源、等级和操作编号查询错误。
- `GET /api/operations/latest`：最近操作与可恢复进度。
- `GET /api/operations/<id>`：单次操作详情、步骤、日志和结果。
- `POST /api/operations`：创建白名单操作。
- `POST /api/operations/<id>/confirm`：确认修复、停止 Docker 或初始化数据。
- `POST /api/operations/<id>/retry`：从失败步骤重试。
- `GET /api/logs`：读取白名单服务脱敏日志。

现有 `/api/action`、`/api/checks` 和 `/api/checks/latest` 在迁移期保留兼容，但页面新代码统一使用操作资源。接口不接受任意命令字符串。

## 8. 验收标准

### 运行可靠性

- 只启动控制台不会启动 Docker 或项目服务。
- 一键启动能按固定顺序启动完整项目，并显示每一步状态。
- 一键停止不会停止控制台和 Docker/Colima。
- 端口、进程、代理目标和可信来源不一致时能阻断并指出具体证据。
- 浏览器刷新或控制台页面重开后能恢复当前操作状态。

### 登录与验收真实性

- 正常 `/api/login/` 登录通过才可以标记真实登录验收通过。
- `/api/demo-login/` 通过不能替代真实登录。
- `127.0.0.1:5173` 和 `localhost:5173` 两条入口都必须明确显示结果。
- 登录失败必须保留 HTTP 状态、错误原因、来源校验和前端错误证据。

### 诊断与修复

- 当前已知的 `5173 -> 8001` 与 `5175` CSRF 白名单冲突能被稳定识别。
- “修复并重试”完成后重新读取真实配置、重启受影响服务并重新执行真实登录。
- 错误历史至少保留 7 天，自动脱敏，控制台重启后可查询。
- 所有危险操作均有确认和操作记录。

### 自动化验证

- 控制台单元测试覆盖运行契约、端口冲突、CSRF/CORS 诊断、进度状态机、白名单动作、脱敏和确认规则。
- 真实登录脚本覆盖账号密码登录失败、CSRF 来源失败、代理不可达和成功登录。
- E2E 不再只依赖 `demo-login`，至少包含一次真实 `/api/login/`。
- 控制台启动、项目启停、完整验收和浏览器刷新恢复均有测试。
- 不执行真实 Docker/Colima 破坏性操作的测试使用 mock 或 dry-run。

## 9. 非目标

- 不做远程服务器管理。
- 不做多用户控制台账号体系。
- 不做任意终端或远程 Shell。
- 不替代 Docker Desktop、Colima 或 CI/CD 平台。
- 不把项目业务错误自动修改成未知的“修复结果”；业务数据变更仍需业务页面确认。
