## 0. 一句话结论

灵溯已经是一个**业务闭环完整、测试覆盖扎实**的 K12 科创协作平台原型，后端状态机与权限边界做得很严谨；但**工程化投产条件尚未就绪**——无版本控制、无自动化 E2E、无 CI、核心视图文件过大。当前状态更准确地说是"**可受控试点的 MVP 候选**"，而非"生产级完成"。建议按 P0→P1→P2 顺序补齐后再对外宣称投产。

---

## 1. 项目定位与价值

- **做什么**：面向学校的青少年科创项目协作平台。学生走"立项→材料沉淀→报告导出"，教师逐项审核，平台管学校授权/赛事/案例治理，AI 只给可编辑草稿并留痕。
- **核心差异化**：严格的数据隔离（按学校过滤）、不可绕过且可追溯的业务状态机、AI 辅助不替代学生原创。
- **目标用户**：学校管理员、指导教师、学生三端。

## 2. 技术架构（已验证）

| 层 | 技术 | 备注 |
| --- | --- | --- |
| 前端 | Vue 3 + Vite + TS + Element Plus + Pinia + Vue Router | 暖白北欧研究手帐风格 |
| 后端 | Django 5.1 + DRF + PostgreSQL + Celery + Redis | 单体 Django app `apps/core` |
| 基础设施 | Docker Compose（postgres/redis/clamav/celery/gotenberg/nginx） | Gotenberg 做 DOCX→PDF，ClamAV 扫描 |
| 异步 | Celery worker + beat | AI 生成、报告导出、文件扫描 |
| 文件 | 分片上传 + SHA-256 + 私有附件 + ClamAV | 500MB 上限，>8MB 自动分片 |

**架构评价**：边界清晰、职责分明。后端把状态校验从 `views.py` 抽到了 `workflows/`（已落地 `ai/materials/projects/cases/memberships` 五个领域服务），这是非常正确的架构决策——业务规则集中在可测试的服务层，视图只做 HTTP 编排。

## 4. 业务模型与权限边界（三角色状态机）

后端已实现一套**不可绕过、可追溯**的状态机（来源：`docs/superpowers/plans/2026-08-13-lingsu-business-core.md`，规则 1–9 全部已落地测试）：

- **Project**：`UNCLAIMED → (教师认领) ACTIVE → (任务全完) COMPLETED`
- **ProjectTask**：`LOCKED → AVAILABLE → PENDING_REVIEW → APPROVED/REVISION_REQUIRED → COMPLETED`（前序解锁后序）
- **MaterialRevision**：`DRAFT → (leader+truth_confirmed) SUBMITTED → (教师) APPROVED / REVISION_REQUIRED`
- **PublicCaseRequest**：`PENDING_TEACHER → (教师) → (admin 可见性) PUBLISHED / OFFLINE`

**三角色硬边界**（实测有测试保护）：
- **student**：建草稿、认领后建任务链、提交需 `truth_confirmed`、AI 扣配额留 `AIGenerationLog`、申请公开（仅 leader）。看不到他人/他校。
- **teacher**：认领 UNCLAIMED、审材料（仅主指导且须填意见）、确认成员、管模板/赛事一级审。不可管非本人项目。
- **platform_admin**：管学校（license/ai_quota/storage/邀请码）、唯一管赛事、平台公告、案例二级治理。**不可访问任何学校项目/材料/成员/AI 过程数据**（直接 403）。

**评价**：这是项目最成熟的部分，也是它相对于"演示型原型"的核心壁垒。

## 6. 投产前缺口与风险（实测未达标项已标 ⚠）

### ⚠ P0：必须补齐（实测多数未完成）
1. **无版本控制**：`git rev-parse` 确认**不是 Git 仓库**。无任何提交历史、无分支保护、无回滚能力——这是投产最大硬伤。
2. **无浏览器 E2E**：`frontend/e2e/` 不存在、`playwright.config.ts` 不存在。三条核心链路（登录路由 / 提交-打回-重提-通过 / 授权只读）仍靠人工点击，**无自动化回归保护**。
3. **无 CI/CD**：`.github/workflows/` 目录为空，质量门禁（单元+类型+构建+E2E）未自动化。
4. **views.py 未拆分**：实测 **1189 行**，超出 600 行目标近一倍，维护风险高（business-core 计划任务 7 列为"后续批次"）。
5. 写操作反馈统一化仍有缺口：AI 中心、教师公告、公开案例、成员邀请、材料上传的加载/成功/失败/重试状态需逐项核对。

### P1：下一阶段
1. 进一步拆分 `StudentProject.vue` / `TeacherWorkbench.vue` / `PlatformConsole.vue` 大分支为独立路由 + Pinia store 模块。
2. 教师风险面板、版本差异、最近活动；平台学校详情编辑+审计记录。
3. 统一 `OperationToast` / `ProgressRail` / `EmptyState` 反馈组件。
4. AI 中心补齐"服务状态→配额→失败重试→预览→明确采用→写入草稿"完整交互。

### P2：试点前保障
1. 真实上传进度、解析/OCR、报告导出排队与失败重试。
2. 可访问性（axe 扫描、键盘焦点、对比度、1280/1440 与窄屏重排）。
3. 依赖审计、备份恢复演练（脚本已存在 `scripts/backup.sh` `restore.sh`，但需演练）、跨校越权专项测试、试点操作手册。

## 8. 下一步优先级建议

1. **立即**：`git init` + 首提交 + 建立 `main` 保护分支（哪怕是单人开发，也要先有历史与回滚能力）。
2. **本周**：落地 Playwright E2E 三条核心链路（复用 pilot-readiness 计划任务 1 的 spec 设计），补齐 CI 质量门禁。
3. **并行**：拆分 `views.py` 到 <600 行（按认证/项目/材料/内容/平台分模块），降低后续改动回归风险。
4. **试点前**：执行一次隔离环境备份恢复演练，跑通 500MB 上传+Celery 失败恢复+跨校越权专项。
