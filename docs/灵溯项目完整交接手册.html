3.3 主要状态机

  • 任务：available → pending_review → approved/completed，打回为 revision_required
  • 材料/修订：draft → submitted → approved，打回为 revision_required
  • 成员邀请：pending_student → pending_teacher → approved，任一环节可拒绝
  • 公开案例：学生校内申请或教师全平台邀请；全平台路径要求学生同意和平台审核
  • AI 生成：queued → processing → completed/failed
  • 报告导出：queued → processing → completed/failed

3.4 AI 的产品边界

AI 是可追溯的辅助工具，不应替学生编造数据或自动提交。系统保存输入、上下文范围、引用来源、生成结果、核验项和采用到材料的关联。学生/教师对话分为开题、研究、答辩工作区。

本地最新版新增平台 AI 密钥配置，使用加密字段保存；该能力依赖迁移 0041_platform_ai_configuration，生产尚未具备。

6.2 不可破坏的权限规则

  1. 所有学校业务对象必须按当前用户学校过滤。
  2. 学生只能访问自己领导或加入的项目。
  3. 教师只能管理本人指导项目；认领时使用事务锁避免竞争。
  4. 平台管理员不能读取学校项目成员、材料和 AI 过程数据。
  5. 正式材料提交必须由项目负责人执行，并确认真实性。
  6. 材料审核必须由主指导教师执行并留下意见。
  7. AI 输出保存为材料时必须保留生成记录与材料修订的关联。
  8. 附件下载必须经过 Django 权限检查，不能改成公共媒体 URL。
  9. 全平台案例发布必须保留学生同意和平台审核记录。

6.3 数据持久化

生产命名卷：postgres_data、media_data、redis_data。PostgreSQL 是业务事实源；媒体卷存储私有附件；Redis 主要用于队列，不应被当作永久业务数据库。

生产部署、恢复或服务器迁移必须同时处理 PostgreSQL 与 media_data。只备份数据库会导致附件记录存在但文件丢失。

10. 安全发布与回滚

当前发布冻结： 在生产备份完成隔离恢复演练、迁移 0040/0041 验证通过、固定镜像 SHA、补齐 AI_CONFIG_ENCRYPTION_KEY 并完成核心烟雾测试之前，禁止发布当前本地最新版。接手初期只允许巡检和备份。

10.0 解除发布冻结的条件

  • 数据库、媒体、环境快照已生成并复制到服务器之外。
  • 在隔离环境完整恢复成功，三角色能登录并查看预期数据。
  • 迁移 0040/0041 在生产副本上通过，耗时和结果已记录。
  • 当前运行镜像和新镜像均使用完整 Git SHA，可拉取。
  • AI_CONFIG_ENCRYPTION_KEY 已生成并存入密码管理器。
  • E2E 失败原因已修复，或至少人工完成核心烟雾测试并签字。
  • 发布、回滚负责人及维护窗口已经确认。

10.1 发布前清单

  • 新负责人批准变更窗口。
  • 数据库备份能被 pg_restore --list 读取。
  • 媒体归档存在且大小合理。
  • 备份已复制到服务器之外的加密存储。
  • 记录当前后端/Web 镜像 SHA。
  • 新镜像与代码提交一一对应。
  • 在隔离环境完成迁移和烟雾测试。
  • 准备旧镜像标签与数据库恢复点。
  • 明确回滚负责人和允许停机时间。

10.2 建议发布顺序

以下均为 [高风险]，这里只描述顺序，不授权直接执行：

  1. 冻结写入或进入维护窗口。
  2. 执行并异地保存数据库、媒体和环境快照。
  3. 拉取固定 SHA 镜像，不使用浮动 latest。
  4. 先执行迁移评估，再应用迁移。
  5. 更新 backend、celery、nginx，不重建 PostgreSQL 卷。

10.3 回滚触发条件

  • 健康接口失败或容器反复重启。
  • 登录/权限隔离异常。
  • 新写入失败、迁移异常或数据数量突变。
  • 学生提交、教师审核等核心流程阻断。
  • AI 配置无法解密且影响现网功能。

代码镜像可以回退，数据库结构不一定能安全反向迁移。涉及 0040/0041 的回滚应优先使用发布前完整备份在维护窗口恢复，不能盲目执行 migrate core 0039。

    密码是上一步刚设置的本地临时密码。成功标准：三个账号都能登录到对应入口。

  5. 只有明确要清空并重建演示数据时才使用 --reset。生产服务器永远禁止执行。

16.3 每次接手代码后的本地验收

执行人： 开发负责人。

执行时机： 拉取代码后、准备发布前、合并重要改动前。

  1. 确认代码状态：

    # [只读]
git status --short
git branch --show-current
git log -5 --oneline

    如果存在不认识的本地修改，先确认归属，不要覆盖或丢弃。

  2. 前端测试和构建：

    cd frontend
npm ci
npm test
npm run build
cd ..

    成功标准：测试 0 failed；npm run build 退出码为 0。包体积 warning 可以记录，但 error 不能忽略。

  3. 后端检查：

    docker compose --env-file .env.integration exec -T backend python manage.py check
docker compose --env-file .env.integration exec -T backend python manage.py makemigrations --check --dry-run
docker compose --env-file .env.integration exec -T backend python manage.py test apps.core.tests --keepdb

    成功标准：系统检查 0 issue、No changes detected、测试 0 failed。

  4. E2E 当前不是稳定基线。运行前确认无人同时重置 E2E 数据：

    cd frontend
npm run test:e2e

    成功标准：25 项全部通过且进程自行退出。若出现 seed_core_e2e --reset 冲突，先停止并确认没有第二个 Playwright 进程；不要并发重复运行。

16.4 线上每日巡检

执行人： 运维负责人。

执行位置： 任意已配置新负责人 SSH Key 的安全电脑。

影响： 以下全部只读。

  1. 登录并确认身份：

    ssh ubuntu@1.15.230.239
id
hostname
date -Is

    成功标准：用户为 ubuntu，主机名为 VM-0-12-ubuntu，时间正确。

  2. 进入部署目录并检查服务：

    cd /home/ubuntu/lingsu
docker compose ps

    成功标准：backend、postgres、redis healthy；celery、nginx Up。任何容器 Restarting、Exited 或 unhealthy 都是异常。

  3. 检查 API：

    curl -fsS http://127.0.0.1/api/health/

    当前正常结果：status=ok；附件和 PDF 为 false 是当前生产配置，不需要为此重启。

  4. 检查资源：

    df -h /
free -h
swapon --show

    处理标准：根盘超过 75% 开始排查，超过 85% 立即告警；不要直接删除 Docker 卷。

  5. 检查最近错误：

    docker logs --since 24h --tail 500 lingsu-backend-1 2>&1 | grep -Ei 'error|exception|critical|fatal' | tail -30
docker logs --since 24h --tail 500 lingsu-celery-1 2>&1 | grep -Ei 'error|exception|critical|fatal' | tail -30

    没有输出表示这段日志未命中关键词，不等于系统绝对无问题。出现错误时记录时间、容器、错误摘要；日志若含用户内容必须脱敏。

  6. 退出服务器：

    exit

16.5 第一次建立生产备份

执行人： 新运维负责人。

风险： [高风险]。虽然备份不应修改业务数据，但会读取全库、占用磁盘并保存敏感环境快照。必须先获得新负责人批准，在低峰期执行。

  1. 登录后检查预计空间：

    ssh ubuntu@1.15.230.239
cd /home/ubuntu/lingsu
df -h /
docker compose exec -T postgres sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atc "select pg_size_pretty(pg_database_size(current_database()));"'

  2. 创建只允许当前用户访问的备份根目录：

    # [变更]
install -d -m 700 /home/ubuntu/backups

  3. 执行项目备份脚本：

    # [高风险]
BACKUP_ROOT=/home/ubuntu/backups BACKUP_RETENTION_DAYS=30 ./scripts/backup.sh

    成功标准：最后输出 Backup created: 和时间戳目录，没有 error。

  4. 检查备份，不读取其中的密钥值：

    latest=$(find /home/ubuntu/backups -mindepth 1 -maxdepth 1 -type d | sort | tail -1)
test -n "$latest"
ls -lh "$latest"
docker compose exec -T postgres pg_restore --list < "$latest/database.dump" | head
test -s "$latest/media.tar.gz"
test -s "$latest/environment.snapshot"

    成功标准：三个文件均非空，容器内的 pg_restore --list 能列出数据库对象。

  5. 把整个时间戳目录复制到服务器之外的加密存储。只有服务器本机副本不算灾备。

  6. 不要在生产直接运行 restore.sh 验证恢复。应在隔离服务器或隔离数据库演练。

16.6 隔离恢复演练

执行人： 运维负责人和开发负责人共同执行。

执行位置： 一台不对外提供业务的隔离服务器，或明确使用独立 Docker 项目名、独立端口和独立卷的测试主机。严禁在生产目录和生产 Docker context 中执行。

完成标准： 只有“数据库恢复成功、媒体恢复成功、对应版本服务启动成功、三角色登录成功、数据基线核对通过”五项全部满足，备份才可标记为“已验证”。

  1. 从生产备份中选择一个明确时间戳目录，不允许自动选择“最新”后直接恢复。记录目录名、文件大小和 SHA-256：

    # [只读] 在备份存放位置执行
backup_dir=/安全备份位置/YYYYMMDDTHHMMSSZ
test -s "$backup_dir/database.dump"
test -s "$backup_dir/media.tar.gz"
sha256sum "$backup_dir/database.dump" "$backup_dir/media.tar.gz"

  2. 在隔离主机建立单独目录，复制与备份时相匹配的代码/镜像、备份文件和专用环境配置。数据库名、端口、Compose 项目名均不得与生产相同。

  3. 启动隔离 PostgreSQL 和 Redis，确认容器名不含生产正在运行的实例：

    # [变更] 仅隔离环境
docker compose -p lingsu-restore-drill --env-file .env.restore up -d postgres redis
docker compose -p lingsu-restore-drill --env-file .env.restore ps

  4. 把数据库备份恢复到隔离数据库。下面的 restore-postgres-1 必须先用上一条 ps 确认是隔离容器：

    # [高风险] 仅隔离环境
docker exec -i lingsu-restore-drill-postgres-1 sh -lc \
  'pg_restore --clean --if-exists --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < "$backup_dir/database.dump"

  5. 恢复媒体到隔离环境的 media_data 卷，不能挂载生产媒体卷。启动对应版本 backend、celery、nginx 后检查：

    # [变更] 仅隔离环境
docker compose -p lingsu-restore-drill --env-file .env.restore \
  --profile production --profile async up -d backend celery nginx
docker compose -p lingsu-restore-drill --env-file .env.restore ps
curl -fsS http://127.0.0.1:隔离端口/api/health/

    隔离端口 必须替换为 .env.restore 中明确配置、且不与生产冲突的实际端口。

  6. 验证三类角色登录、项目列表、材料数量和最近项目时间。把结果与第 8.6 节的备份时点数据基线比较；合理新增可以接受，减少必须解释。

  7. 填写恢复演练记录：备份时间、镜像 SHA、开始/结束时间、恢复耗时、执行人、数据核对结果、失败与修复过程。

  8. 演练完成后只清理 lingsu-restore-drill 项目。先再次核对项目名，再执行：

    # [高风险] 仅隔离环境
docker compose -p lingsu-restore-drill --env-file .env.restore down -v

    生产项目绝对禁止执行 down -v。

16.8 回滚操作

  1. 仅前端异常且数据库/后端正常： 把 WEB_IMAGE 改回发布单记录的旧 SHA，执行 Nginx 的 up -d --no-build，再验证页面。

  2. 后端异常但没有执行新迁移或新数据写入： 把 BACKEND_IMAGE 改回旧 SHA，更新 backend/celery，再验证健康和权限。

  3. 已经应用 0040/0041 或产生新数据： 不要直接降级迁移。进入维护窗口，在隔离环境先验证发布前备份；由数据库负责人决定恢复整个数据库和媒体，而不是只回退镜像。

  4. 恢复脚本会清理现有数据库对象、删除媒体内容并重启服务：

    # [高风险] 仅展示，未经批准禁止在生产执行
backup_dir=/home/ubuntu/backups/发布单中记录的明确时间戳
test -s "$backup_dir/database.dump"
test -s "$backup_dir/media.tar.gz"
./scripts/restore.sh "$backup_dir"

  5. 回滚后必须再次检查容器、健康接口、迁移状态、三角色登录和核心业务数据；记录原因和受影响时间段。

16.9 常见故障的明确处理顺序

网页打不开

  1. 从外部浏览器确认是否所有人都打不开。
  2. SSH 登录，执行 docker compose ps。
  3. Nginx 不在 Up：查看 docker logs --tail 200 lingsu-nginx-1。
  4. Nginx 正常：执行 curl -I http://127.0.0.1/。
  5. 本机能访问、外部不能访问：检查云安全组、防火墙和域名，不要重启数据库。

API 或登录失败

  1. 执行 curl -fsS http://127.0.0.1/api/health/。
  2. 失败时检查 backend、postgres、redis 是否 healthy。
  3. 查看 backend 最近 200 行日志。
  4. 如果出现数据库连接错误，先检查 PostgreSQL 状态和磁盘；不要修改数据库密码碰运气。
  5. 如果只出现 CSRF/403，核对访问域名是否在允许域名和 CSRF 来源配置中。

AI 一直排队

  1. 检查 lingsu-celery-1 是否 Up。
  2. 查看 Celery 日志是否有认证、限流、网络或模型错误。
  3. 在平台状态页确认 AI 是否配置和可用。
  4. 认证错误时轮换/修复 Key；不要把 Key 打印到终端记录或工单。
  5. 保留失败的 AI 日志用于审计，不直接改数据库状态为 completed。

磁盘不足

  1. 执行 df -h / 和 docker system df。
  2. 找出增长来源：容器日志、旧镜像、备份或媒体。
  3. 先转移备份、设置日志轮转；确认镜像不再用于回滚后再清理旧镜像。
  4. 永远不要删除 postgres_data、media_data，也不要运行 docker compose down -v。
